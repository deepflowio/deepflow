## 4. 第一个提交的冲突处理

### 4.1 eBPF syscall 地址采集

`2df1d0a` 的主要冲突文件为：

```text
agent/src/ebpf/kernel/socket_trace.bpf.c
agent/src/ebpf/test/test_udp_local_addr_contracts.py
agent/src/ebpf/user/socket.c
agent/src/ebpf/user/socket.h
```

处理原则是保留上游提交的行为目标，但适配 v6.6 已有的入口/退出 Hook 结构，而不是机械采用冲突任一侧。

最终代码仍保留 `__sys_sendmsg()` 入口和退出处理，并没有删除 sendmsg 支持：

- `sendmsg()` 的目标地址是输入参数，入口直接按 `msg_namelen` 校验并提取。
- `recvmsg()` 的 `msg_name` 是输出缓冲区，入口保存指针和调用者提供的容量，退出时再提取实际地址。
- `sendmmsg()` / `recvmmsg()` 保存当前消息的 `msg_name`、地址容量和 `msg_len`，避免复用旧 UDP 远端地址。
- `addr` 与 `ipaddr_ptr` 共用 union，退出时先把指针保存到局部变量并清空 union，再写入归一化地址，避免旧指针位残留在地址字段。

`recvmsg()` 入口中的代码：

```c
/* 保存入口容量；返回后的 msg_namelen 不能代表实际复制长度。 */
read_args.port =
    normalize_sockaddr_capacity(msghdr->msg_namelen);
```

含义是：内核返回后会把 `msg_namelen` 更新为完整源地址结构需要的长度，但用户实际传入的缓冲区可能更短。例如 IPv6 返回值可为 28，而入口容量只有 16；此时只能读取入口实际允许内核写入的 16 字节，不能依据返回后的 28 字节越界读取用户缓冲区。`port` 在入口到退出之间被临时复用为归一化后的 sockaddr 容量，提取后再恢复其正常地址字段语义。

### 4.2 datadump 元数据与公开 ABI

v6.6 没有增加公开 callback 结构体字段。内部 reader 到 datadump 的传递临时借用 64 位
`syscall_len` 高 32 位携带 `SOURCE_FN` 和 `MSG_NUM`，datadump 读取后，在调用外部 callback 前执行：

```c
sd->syscall_len = (uint32_t)sd->syscall_len;
```

当前代码位于 `agent/src/ebpf/user/socket.h:420`。冲突本身靠近原有 callback 前时间戳处理和相邻注释；合并后的关键约束是先让 datadump 看见内部元数据，再把公开字段恢复为真实报文长度，最后调用 callback。因此测试日志中 callback 的 `syscall_len` 仍为 24、37 等真实长度，高位不会泄漏给上层。

### 4.3 4.14.15 skb 布局没有被“删除”

上游版本在 UDP 本地地址补偿模块中加入过以下精确版本判断：

```c
if (!strcmp(linux_release, "4.14.15-1.el7.elrepo.x86_64") ||
    !strcmp(linux_release, "4.19.17-1.el7.x86_64")) {
```

v6.6 根本没有该 UDP 本地 IP 补偿函数及其所在模块，因此没有可合并的位置。回迁时不是从 v6.6 删除已有代码，而是没有额外引入整套缺失模块及其固定 skb offset。该差异已写入 `2df1d0a` 的提交说明。

其直接影响是：通配地址绑定时如果本地 IP 仍为 `0.0.0.0` 或 `::`，PeerKey 端点不完整，UDP peer 隔离按设计回退到物理 socket ID。

### 4.4 LLVM 11 栈限制适配

上游实现中第二条 mmsg 长度的局部变量布局在 v6.6 的 LLVM 11 构建链上会导致 BPF 栈超限。回迁版本改为直接把第二条消息长度读入待提交事件，减少栈占用，同时保留第二条消息独立长度和部分成功语义。

## 5. 第二个提交的适配

`b936c16` 修正 `mmsghdr.msg_len` 的栈槽处理：

- `msg_len` 本身是 4 字节 `unsigned int`。
- 本地 `bytes_count` 继续使用清零的 8 字节 `ssize_t` 栈槽，以维持 verifier 稳定的栈布局和寄存器分配。
- `bpf_probe_read_user()` 只读取低 4 字节，避免把结构体 padding 当成长度高位。

这个提交在单独验证时解决了 5.2+ 内核上 mmsg 退出程序达到 verifier 复杂度上限的问题。但第三个 UDP peer 提交又显著增加了大函数状态空间，因此不能据此推导合并三项后的 5.10 版本仍必然可加载；后续在 192.168.10.12 上的失败正是新增组合问题。

## 11. 192.168.10.12 加载失败诊断

### 11.1 现象与环境

目标机环境：

- Linux `5.10.201-1.el7.x86_64`
- CentOS 7
- `/sys/kernel/btf/vmlinux` 存在
- 进程具备包括 `CAP_SYS_ADMIN`、`CAP_BPF` 在内的所需权限
- loader 正确选择 `socket-trace-bpf-linux-5.2_plus`

失败日志：

```text
[eBPF] WARN func load_ebpf_object() [user/tracer.c:607] bpf load 'socket-trace-bpf-linux-5.2_plus' failed, error:Argument list too long (7).
```

这里的 errno 7 是 `E2BIG`，由 BPF verifier 拒绝程序产生，不是 shell 命令参数真的过长。

### 11.2 当前根因结论

v6.6 的 `LINUX_VER_5_2_PLUS` 路径仍在主程序中直接内联调用
`__output_data_common()`，当前位置为
`agent/src/ebpf/kernel/socket_trace.bpf.c:1802`。

当前 5.2+ ELF 中两个关键程序的静态规模为：

```text
sys_exit_sendmmsg  21661 条指令
sys_exit_recvmmsg  21743 条指令
```

进一步使用同一 Docker 镜像、同一 LLVM 11 构建链复编译 `b936c16` 基线，结果为：

```text
b936c16 sys_exit_sendmmsg  24888 条指令
b936c16 sys_exit_recvmmsg  24961 条指令
3f537eb sys_exit_sendmmsg  21661 条指令
3f537eb sys_exit_recvmmsg  21743 条指令
```

`b936c16` 的程序静态指令更多，但其提交验证记录显示能在同一 Linux
`5.10.201-1.el7.x86_64` 加载；`3f537eb` 的指令更少却返回 E2BIG。因此根因不能表述为“静态指令条数过多”，而是第三个提交改变了分支、Map 访问、栈布局和寄存器状态后，5.10 verifier 探索的状态空间超过限制。

另一个关键功能缺口是：当前 `rewrite_udp_peer_metadata()` 只有一处调用，位于
`output_data_common()` 的 tail-call 输出程序。`LINUX_VER_5_2_PLUS` / `LINUX_VER_KFUNC`
走的是 `__output_data_common()` 直连路径，该函数调用
`output_extra_data_common(..., NULL, 0, ...)`，没有执行 peer metadata 重写。因此当前版本即使绕过加载失败，5.10 的 5.2+ 变体也不会真正获得 peer socket ID 隔离。

loader 当前调用 `bcc_prog_load()` 时使用 `log_level=0`，代码位于
`agent/src/ebpf/user/load.c:603`，并临时重定向 stderr，所以日志只保留笼统的 E2BIG，没有 verifier 的详细状态爆炸位置。

### 11.3 直接补进 5.2+ 内核路径不可行

在独立临时副本中做过以下无 tail-call 实验：

1. 恢复主 iovec 复制路径，不再给 18 次展开循环增加运行时 `loop_limit` 条件。
2. 为第二条 sendmmsg 消息单独保留一次 iovec 复制函数。
3. 在 `__output_data_common()` 中补入 `PeerKey`、peer ID 重写和第二条消息序号更新。

该版本尚未生成 ELF，LLVM 11 在编译阶段即报告多个入口的 BPF 栈超过 512 字节，典型错误为：

```text
Looks like the BPF stack limit of 512 bytes is exceeded.
Please move large on stack variables into BPF per-cpu array map.
```

这说明不能只把 v7.1 输出程序中的栈上 `PeerKey` 搬到 v6.6 的 5.2+ 直连大函数。即使改用 per-CPU scratch Map 消除栈变量，peer Map 的查找、创建、原子序号和 sendmmsg 二次查找仍会加入已经很复杂的主程序，仍需重新面对 5.10 verifier 状态上限，风险较高。

### 11.4 不使用 tail-call 的推荐方案

如果确定继续基于 v6.6 且不采用 v7.1 tail-call，推荐将 UDP peer ID 和 peer
`cap_seq` 的重写移到 C 用户态。该方案符合原设计“只改写提交给上层的元数据，内核原有 socket 状态继续使用物理 ID”的边界，同时彻底移除新增 peer 逻辑对 eBPF verifier 的影响。

实施步骤：

1. **恢复 eBPF 直连路径**：从 `socket_trace.bpf.c` 移除 UDP peer key/state、LRU Map、重写函数和 sendmmsg peer 二次查询；保留前两个提交的 UDP 地址采集、mmsg 长度和 verifier 栈槽修复，使 5.2+ 程序回到已在 5.10 验证可加载的 `b936c16` 形态。
2. **保留配置 ABI**：继续保留 `udp_peer_id_enabled` 的 Rust 配置项和 C FFI setter，但 setter 改为控制用户态 peer cache，不再写 eBPF enabled Map。
3. **增加用户态 PeerKey**：Key 包含物理 `socket_id`、地址族、完整本地/远端地址和端口；只处理 UDP、非关闭事件和完整端点，其余继续输出物理元数据。
4. **在入队前重写**：在 `reader_raw_cb()` 把 `__socket_data` 转成
   `socket_bpf_data` 后、进入 dispatch queue 和 datadump 前完成重写，确保 datadump 与公开 callback 看见相同的 peer `socket_id` / `cap_seq`。
5. **使用有界并发缓存**：实现容量 40960 的分片 Hash + LRU，分片锁保护创建、查找和 `seq` 递增；Map 分配失败或容量处理失败时回退物理元数据。
6. **生成 peer ID**：使用进程启动随机种子对完整 PeerKey 做 64 位哈希，并维护反向 ID 表检测活动项冲突；冲突时使用递增 salt 重新计算。这样不依赖内核 `tracer_ctx_map` 的 per-CPU ID 分配，也不会改变公开 ABI。
7. **保持 sendmmsg 连续性**：同一 perf buffer 中的两条 sendmmsg 事件按原顺序在
   `reader_raw_cb()` 内处理，对同一 PeerKey 连续分配 `cap_seq=0,1`。
8. **配置关闭/重启清理**：关闭功能或停止 tracer 时释放 peer cache；重新开启后从
   `cap_seq=0` 开始，避免跨配置周期复用旧状态。

该方案能解决当前 5.10 加载问题，因为 5.2+ ELF 不再包含第三个提交新增的 peer verifier 路径；同时能修复当前 5.2+ 直连路径实际上没有执行 peer 重写的功能缺口。

需要明确的差异是：peer LRU 从 BPF Map 变为用户态缓存，Map 容量测试和设计文档要同步调整。多 perf reader 并发时由分片锁定义 peer 序号的提交顺序；必须增加跨 CPU/跨队列压力测试，确认该顺序满足上层关联要求。

### 11.5 备选内核方案及风险

如果强制要求 peer ID 和 `cap_seq` 必须在内核中生成，又不允许 tail-call，则需要新增
per-CPU scratch Map 保存 PeerKey 和临时 state，避免 512 字节栈超限；同时要把主 iovec
复制与第二条消息复制拆成编译期固定循环，尽量减少 verifier 分支。

该方案仍把 Map lookup/update/XADD 引入 5.2+ 大函数，不能仅凭编译通过判断可用，必须在
5.10 获取完整 verifier log 并反复裁剪状态。相比用户态方案，它改动更脆弱、跨内核验证成本更高，目前不作为推荐方案。
